## 0. 结论速览

1. **基线复跑成功**：`baseline.md` 的指纹数字复现——SQLite 写入 **36 req/s**（文档 35）、
   PG 低负载写入 **P99 116ms**（文档 133ms）。可以做增量对比。
2. **上一版的根因判断是错的**。连接池开到与并发齐平（60）后，P99 **没有改善**
   （1778 → 2146ms）。同一服务上跑并发曲线：8/15/30/60/90 workers 的吞吐是
   **78/79/78/77/76 req/s——完全不变**。这不是"池不够"，是**存在一个串行资源**。
3. **真正的约束是数据库的"事务吞吐"，而每请求的事务数高得离谱**：
   PG 日志实测 **15.1 条 SQL / 4~5 次事务 / 请求**（`state_kv` 行写 2.71 次、业务行写 ~1 次）。
   本机 PG 容器的事务上限实测 **143/s（单连接）/ 513/s（20 并发）**；
   `5 次事务 × 80 req/s ≈ 400/s` 已贴住该上限 → **天花板 ≈100 req/s**，与实测 70~90 吻合。
4. **T1 交付了两件事**：① **SQLite WAL 是确证的大改善**（写入 30 → **64 req/s**，
   P99 5281 → **1909ms**，3 次重复稳定）；② 连接池可配 + 候选索引去重（热路径少一次全局行锁写）。
   **但 PG 中负载 P99 仍是 ~1.4~2.1s，SLO（≤500ms）未达标**，且**靠调参达不到**。
5. ⚠️ **本节第 2/3 条的根因判断已被 §6 的实测再次修正**（T1.5 已实施）：每请求事务数
   确实从 **9.16 降到 7.13（−22%）**，但 **P99 一动不动**（3124 → 3078 ms）。真约束是
   **每请求 ~16 条 SQL 往返 × 单次往返 ~3 ms**，不是提交吞吐（压测中 PG 31 个后端
   **全是 `ClientRead`**、在等客户端）。**SLO 仍未达标**：最优 P99 **1298 ms**
   （4 workers），目标 ≤500 ms。横向扩展也在 **2 个 worker 就饱和（~70 req/s）**。见 §6。

## 2. 根因（含对上一版结论的推翻）

### 2.1 ❌ 上一版说"连接池饱和"——被三个实验推翻

上一版的核心论证是"60 并发打默认池（5+10=15）⇒ 吞吐与 15 并发相同、P99 差 6.1 倍"。
**观测是真的，解释是错的**：

| 实验 | 结果 | 说明 |
|---|---|---|
| 池开到 **60**（对齐 60 workers） | 70 req/s，**P99 2146ms**（对比默认池 1778ms） | **没有改善** → 池不是约束 |
| 并发曲线（同一服务，只改 workers） | 8w→78、15w→79、30w→78、60w→77、90w→76 req/s | **吞吐恒定** → 存在串行资源 |
| 60w 压测期间 PG 活跃连接 | **17~23**（≈池上限 20） | 连接虽被占满，但**加大池无用** ⇒ 瓶颈在库不在池 |
| 数据面 CPU 成本（300 次 `process_batch`） | **0.05 ms/请求** | 不是 CPU/GIL |
| `synchronous_commit=off` | 62 vs 89 req/s（噪声内） | **不是 WAL fsync** |
| 共享状态后端 A/B（同库同负载） | postgres 38/31 req/s vs **memory 47/42** | 状态层占 ~25~35% |

"6.1 倍 P99 差"的正确解释是**排队长度**：固定服务率 μ≈73/s 下，
并发 15 → W≈205ms、并发 60 → W≈757ms（Little 定律 `L=λW` 两边都对得上），
与池容量无关。**在 15 workers 下负载发生器本身提供不了足够并发去暴露排队。**

### 2.2 ✅ 真正的约束：每请求 ~5 次数据库事务

用 PG 自己的日志与统计量实测（单请求顺序发、`log_statement=all`、`pg_stat_database`）：

| 口径 | 每请求 |
|---|---|
| SQL 语句总数 | **15.1** |
| BEGIN / COMMIT / ROLLBACK | **5.0 / 4.1 / 1.0** |
| `state_kv` 行写入 | **2.71** |
| `telemetry_events` + `candidates` 行写入 | ~0.95 |
| 事务数（`xact_commit` 差分） | **8.6~9.1** |
| 同上，但共享状态换 memory（对照） | **2.1** ⇒ **状态层占 ~6.5 次事务/请求** |

本机 PG 容器的事务吞吐上限：**143 commit/s（单连接）**、**513 commit/s（20 并发）**。
`5 次事务 × 80 req/s = 400 txns/s` —— 已贴住上限，**这就是 ~70~90 req/s 天花板的来源**。

热路径上的状态事务来自三处（`state/pg.py::mutate` = 一次 `engine.begin()` + `SELECT … FOR UPDATE`
+ `UPDATE` + `COMMIT`）：

1. **限流**：`rate:{tenant}|{device}`（每次请求 1 次）
2. **候选分组**：`cand:{tenant}|{device}|{component}|{signal}`（每次命中 1 次；多规则命中则多次）
3. **候选索引**：`candidate:index`（**全局单 key**；去重前每次命中 1 次 → 见 §3.2）

业务写入本身只贡献 2.1 次事务（`session_scope` + `_upsert` 的 get/SAVEPOINT/INSERT/RELEASE）。
**所以"先做批量 upsert"是错误的优先级**——它只能动 2.1 那一部分。

## 3. T1 已实施（本轮）

### 3.1 ✅ SQLite：WAL + `synchronous=NORMAL` + `busy_timeout`（**确证有效**）

**完整性复核（防止"数字好看其实是写不进去"）**：另起一次 8 秒写入压测（30 workers），
落库后直接数库：**`telemetry_events` 1202 行 / 请求 1204 次、`candidates` 30 行**
（30 个设备各一条）——写入确实持久化，不是 207 `persist_failed` 的快路径。
另外这次 30 workers 下实测 **143 req/s**，而 60 workers 下只有 **64 req/s**：
同一个库、同一份代码，**并发翻倍吞吐反而减半**，与"SQLite 单写者 + 锁排队/争用主导"
一致（也再次说明压测并发数必须与后端容量匹配，否则测的是排队）。

`storage/db.py::_apply_sqlite_pragmas`，在连接事件上执行；默认开，`DD_SQLITE_WAL=0` 可关。
`engine_kwargs` 的 SQLite 分支**逐字节不变**（有精确断言守着本地行为）。

| 场景（60w@300rps，3 次重复） | 吞吐 | P50 | P99 |
|---|---|---|---|
| `DD_SQLITE_WAL=0`（旧行为） | **30 req/s**（24/30/31） | 1554ms | **5281ms** |
| 默认（WAL 开） | **64 req/s**（61/64/64） | 884ms | **1909ms** |

默认 journal + `synchronous=FULL` 是"每次 COMMIT 一次 fsync"，且写阻塞读；WAL 同时解掉两者。
**这是本轮唯一一个幅度稳定、可复现的改善。**

### 3.2 ✅ 候选索引去重（热路径少一次全局行锁写）

`candidate_shared.py::_register_index` 原本**每次命中**都 `mutate(_INDEX_KEY, …)`——而索引是
**一个全局 key**，在 PG/Redis 后端下就是**全设备、全租户共用一把行锁 + 每次一次提交**。
而它对热路径**毫无收益**：HTTP 走 `build(only_touched=True)`，索引只服务
`build(only_touched=False)` 的运维全量枚举。

改为实例内去重（FIFO 有界 4096；淘汰只导致下次多写一次，不影响正确性）。
单测锁定：同设备 20 次命中 → 索引只写 **1** 次（原来 20 次），且全量枚举完整性不变。

> **诚实说明**：这一项在**单元层面**确证（写入次数 20→1），但在本机**聚合吞吐上没有可测改善**
> （70 vs 72 req/s，噪声内）。它是一次正确的工程修复（去掉热路径上的全局锁），**不是**性能解药。

### 3.3 ✅ 连接池可配（口径修正）

`DD_DB_POOL_SIZE` / `DD_DB_MAX_OVERFLOW`（默认 10+10=20），在 `engine_kwargs` 里接上。
**保留它的理由不是"能治中负载"，而是**：容量必须显式、可审计（库默认 5+10 是隐式的），
且多副本必须满足 `(pool_size+max_overflow) × 副本数 < PG max_connections`。
上一版把它当作主因的表述已在 §2.1 更正。

## 4. 剩余方案（按新证据重新定价）

### T1.5 砍热路径上的状态事务（**新发现，最高杠杆**）

目标：`8.6 → ~3` 次事务/请求。若 DB 事务吞吐确为约束，吞吐应随之 **2~3×**（需实测验证）。

- **限流移出热路径的 DB**：限流桶本就是"允许少量误差"的组件。可选：
  `DD_RATE_BACKEND=redis`（已有开关，走内存级 Redis）、或 `memory`（单副本）、
  或**与候选分组合并到同一次 mutate**（同一事务里读改写两个 key → 省一次提交）。
- **索引写彻底离开热路径**：既然 `build(only_touched=False)` 是运维路径，可改为
  **按前缀扫描**（`StateStore.keys(prefix)` 已存在）枚举，`_INDEX_KEY` 可废弃（保留兼容读）。
- **合并状态事务**：`rate:` 与 `cand:` 两次独立 `engine.begin()` → 一次事务内完成（需给
  `StateStore` 加"批量 mutate"原语，或让候选分组显式携带限流判定）。

### T2 批量 upsert（原方案，**降级为第二优先**）

只影响业务侧的 2.1 次事务：`insert(...).on_conflict_do_update(...)` 单条批量，
语句数从"每行 4 条"降到"每批 1~2 条"；`_upsert` 的 SAVEPOINT/IntegrityError 分支可删。
**预期：+15~25% 吞吐**（而非上一版写的 2~3×，因为状态层才是大头）。

### T3 写队列（仍然是大改，且现在更清楚它的定位）

把**业务落库**移出请求路径；但请注意 §2.2：业务只占 2.1/8.6 次事务，
**先做 T1.5 再评估 T3**，否则会把复杂度花在小头上。语义代价（207 语义、丢数据、背压）同上一版。

## 5. 边界与复现

- **SLO 现状：未达标**（§6 复测后仍如此）。60 workers @300 rps 下最优 P99
  **1298 ms（4 workers）**，目标 ≤500ms——**超标 2.6×**；单进程 **2798~3124 ms**。
  低负载 P99 116 ms 达标；轻并发（8 workers @40 rps）P99 404.6 ms 达标。
  **T1 与 T1.5 都改变不了中负载这件事**：前者是调参，后者砍的是**提交次数**，
  而约束是**往返次数**（§6.3）。要动它得走 §6.5 的两条结构性改动。
- **本机 PG 数字波动 ±25%**（相同配置重复测得 61/70/75/89 req/s）。因此
  **PG 侧 <25% 的差异一律视为噪声**；SQLite 侧差异大且稳定（24/30/31 vs 61/64/64），可信。
- **本机 ≠ 生产**：容器盘 IO、机型、负载发生器都影响结论；`synchronous_commit` 等
  生产可调项需在目标环境复测。
- 复现（PG 容器 + loadgen）：
  ```bash
  docker run -d --name dd_bench_pg -e POSTGRES_USER=ddbench -e POSTGRES_PASSWORD=ddbench_pw \
    -e POSTGRES_DB=ddbench -p 5544:5432 postgres:16-alpine
  # 起服务（DD_DATABASE_URL 指向上面那个库，DD_SERVICE_PORT=8812）后：
  python tools/loadgen.py --url http://127.0.0.1:8812 --mode write \
    --devices 60 --rps 300 --duration 15 --tenant bench-t1 --verify-server --assert-no-llm
  ```
- 每请求事务数/语句数的量法（可复现）：
  `ALTER DATABASE ddbench SET log_statement='all'` → 跑少量顺序请求 → 对 PG 日志做 tail-diff
  数 `BEGIN/COMMIT/ROLLBACK`；行写入数读 `pg_stat_user_tables`；事务总数读 `pg_stat_database.xact_commit`。

## 6. T1.5 已实施 —— 以及**对 §2.2 根因的第二次修正**（2026-10-10 实测）

> §2.1 推翻了"连接池饱和"，把主因判给"**提交吞吐**"。本节实测显示：**那个判断也不对**。
> 提交数确实降下来了（−22%），**P99 一动不动**。真正的约束是**每请求的数据库往返次数**。

### 6.1 T1.5 交付了什么（`mutate_many` + 索引删除）

1. **`StateStore.mutate_many(items)`**：在**一次事务**内对多个 key 做原子 read-modify-write。
   四个后端各自实现（不是纸面契约）：memory 显式回滚、postgres 单事务 +**定序加锁**
   （避免两个批次反向拿锁死锁）、redis 单次 `WATCH/MULTI/EXEC`、基类默认退化为逐个
   `mutate`（正确但仍是 N 次提交——诚实标注在 docstring 里）。
2. **一条事件的全部命中合并成一次提交**（`candidate_shared.py::add`）。旧版每个命中单独
   `mutate`，一条事件常命中 5~6 条规则 → 5~6 次提交。
3. **删除全局索引 key `candidate:index`**：`build(only_touched=False)` 改用**前缀扫描**
   `keys("cand:")`。那条登记只服务运维枚举，却是一把**全局行锁**（§3.2 曾用实例内去重缓解，
   现在是彻底删除）。

### 6.2 实测：**事务数降了 22%，P99 没动**

同机、同参数（PG 16 容器 `@5544`；60 workers @300 rps × 15s）、改动前后**紧挨着各跑一次**，
中间用 `git stash` 切换代码（排除环境漂移）：

| 指标 | before（HEAD） | after（T1.5） |
|---|---|---|
| 完成请求 | 551 | 570 |
| 实测吞吐 | 34 req/s | 36 req/s |
| P50 | 1633.8 ms | 1630.2 ms |
| P95 | 2546.4 ms | 1969.6 ms |
| **P99** | **3124.3 ms** | **3077.8 ms** |
| `xact_commit` 增量 | 5046 | 4065 |
| **每请求事务数** | **9.16** | **7.13（−22%）** |

**结论：提交次数不是约束。** 把 9.16 砍到 7.13（−22%）换来 1.5% 的 P99 变化（噪声内）。
§2.2 那句"`5 次事务 × 80 req/s` 已贴住上限"是**算错了**：同一份数据里本机上限是 513/s，
而 7.13 × 36 = **257 事务/s**，连一半都没到。

### 6.3 第二次修正：约束是**往返次数 × 单次往返成本** —— ⚠️ **本节结论已被 §7 推翻，见 §7.2/§7.4**

三条独立证据（都在本节这次实测里取的）：

1. **PG 全程空闲**。压测中抓 `pg_stat_activity`：**31 个后端全部是 `Client/ClientRead`**
   ——意思是"数据库在等客户端发下一条命令"，没有一个在等锁、等 IO 或跑查询。
   PG 容器 CPU 仅 **23.8%**。
2. **每请求 ~16 条 SQL 往返**。进程内剖析（`cProfile` 跑 300 次真实请求路径）：
   `psycopg` 发出 **4801 条命令 / 300 请求 ≈ 16 条/请求**；`select.select` 占**总耗时
   45%（15.2s / 33.5s）**——这就是往返等待。本机 PG 往返实测 **2.96 ms/次**（暖连接）、
   6.61 ms/次（含建连；本机是 Docker Desktop + WSL2 端口转发，往返成本偏高）。
   `16 条 × 3 ms ≈ 48 ms` 的**串行**往返，就是单请求地板。
3. **服务进程 CPU 很高但 DB 不在等 CPU**：压测期间真身进程（base Python，非 venv 转发壳）
   稳定吃 **137% 单核**。即"往返等待 + 每轮往返的客户端栈开销"共同把单进程服务率钉在
   **~36 req/s**。

### 6.4 横向扩展实测：加 worker 到 2 就饱和

`DD_SERVICE_WORKERS`（本轮新增，多 worker 的正确性前提是状态外置——见
`service/__main__.py` 的**失败关闭**守卫）逐档实测，仍为 60 workers @300 rps：

| workers | 吞吐 | P50 | P95 | **P99** | 事务/请求 |
|---|---|---|---|---|---|
| 1 | 37 req/s | 1563.2 ms | 1963.2 ms | **2797.7 ms** | 7.03 |
| 2 | 70 req/s | 776.4 ms | 1241.2 ms | **1499.1 ms** | 7.00 |
| 4 | 68 req/s | 879.9 ms | 1130.0 ms | **1298.4 ms** | 7.04 |
| 8 | 62 req/s | 924.2 ms | 1266.7 ms | **1542.9 ms** | 7.02 |

**加 worker 到 2 就撞墙（~70 req/s），4/8 反而略降**——因为被共享的串行资源是
**PG/Docker 往返路径**，不是进程数。（每 worker 连接池调成 5+5，避免 8×20 超 PG 上限。）

### 6.5 SLO 现状：**仍未达标**，且**不是调参能解决的**

- 60 workers @300 rps 下最优 P99 = **1298 ms（4 workers）**，目标 **≤500 ms**——**超标 2.6×**。
- 低负载（4 workers @20 rps）P99 **116 ms** 达标（§1）。
- 8 workers @40 rps（轻并发）P99 **404.6 ms**——**达标**；一旦把 offered load 提到远超
  服务率（~36 req/s/进程），延迟就变成**排队主导**（Little 定律 `L=λW`：60 ≈ 36 × 1.67s）。

**下一步的正确优先级（按本轮证据重排）**：
1. **砍往返次数**（不是砍提交次数）：本轮已证明提交数不是约束。真正的大头是那 ~16 条
   SQL/请求。方向：T2 批量 upsert（去掉 `_upsert` 的 get/SAVEPOINT，把"每行 4 条"压成
   "每批 1~2 条"）、以及把**候选分组状态**挪到 Redis（`DD_STATE_BACKEND=redis` 已有，
   sub-ms 且无 SQL 往返）——这两条才直接动"往返次数"。
2. **换掉高往返成本的数据路径**：本机 PG 在 Docker Desktop/WSL2 端口转发后面，
   单次往返 ~3 ms；生产同机直连应显著更低。**这也是"本机 ≠ 生产"最该复测的一项。**

### 6.6 本轮实测的边界（别把这些数字当生产结论）

- **机器不干净**：压测期间另有一个跑飞的 `node`（pi-coding-agent）持续吃 ~115% 单核；
  绝对数字因此偏悲观（同一份文档 §1 的旧基线是 72 req/s，本轮 34~37 req/s）。
  **因此本节所有结论都建立在"同一台机器、紧挨着跑"的 A/B 上，而不是与 §1 的跨时间比较。**
- **`xact_commit` 含只读事务**：它是 PG 实例级计数差分，含后台作业与只读事务，
  不等于"写事务"。故表中"事务/请求"是**同口径可比**的量，不是绝对写次数。
- **进程 CPU 与往返等待的精确切分未完全定论**：进程内 `cProfile` 显示以 `select`
  等待为主（45%），但真身进程在 60 并发下实测吃 137% 单核——两者口径不同
  （前者含 TestClient 的每请求建连，后者含 60 线程的客户端栈开销）。**"往返等待是主因"
  这条结论由证据 1（PG 空闲等客户端）与证据 3（加 worker 在 2 就饱和）支撑，
  不依赖这两者的精确比例。**
- **未做**：Redis 后端下的同一组 A/B、T2 批量 upsert 的实测——那是 §6.5 排出的下一步。

## 7. 第三次修正：**DB 与客户端都不是约束**，且 §6 的测量装置有缺陷（2026-10-10 复测）

> §6.3 把根因判为"**每请求 ~16 条 SQL 往返 × 单次往返 ~3 ms**"，并据此排出了 §6.5 的下一步。
> 本节用四个新实验**推翻了这个判断**，同时**暴露了 §6 那批数字的装置缺陷**——
> 后者更要紧：它意味着 §6 的吞吐/扩展结论**不能再用**。

### 7.1 每请求到底发了哪些 SQL（实测清单，不再是估算）

用一个挂了 `before_cursor_execute` 监听的进程内 `TestClient` 跑 30 次真实请求，把语句按形态归类：

| 条/请求 | 语句 |
|---|---|
| **2.00** | `SELECT value FROM state_kv WHERE key=? FOR UPDATE` |
| **2.00** | `UPDATE state_kv SET value=…, updated_at=? WHERE key=?` |
| 1.00 | `SELECT value FROM state_kv WHERE key=?`（`build()` 读回候选分组） |
| 1.00 | `SELECT set_config(?, ?, true)` ← RLS 租户上下文（每会话一条） |
| 1.00 + 1.00 | `SELECT telemetry_events…`（upsert 前的 get）+ `SAVEPOINT` |
| 1.00 + 1.00 | `INSERT telemetry_events` + `RELEASE SAVEPOINT` |
| ~1.0 + ~1.0 | 候选侧同样的 get / SAVEPOINT / INSERT 或 UPDATE / RELEASE |
| **合计 12.1** | （此前 §2.2 写的是"15.1 条 SQL"，同量级；本节口径更细：含 RLS 与 SAVEPOINT） |

**可直接砍掉的浪费**：`SAVEPOINT`/`RELEASE` 各 1 条/请求（2 条，纯开销）+ upsert 前的两个
`SELECT`（2 条）→ **约 4~5 条/请求（≈40%）可以用 `INSERT … ON CONFLICT DO UPDATE` 一次消掉**
（这就是 §4 的 T2）。**但这不会解决中负载**——见 7.2。

### 7.2 DB 往返通道的容量：**4208 ~ 7795 次/秒**（远未饱和）

从宿主用 1/2/4/8/16/32 个并发连接直接压 PG（`SELECT 1`）：

| 并发连接 | 总往返/s | 单次平均 |
|---|---|---|
| 1 | 505 | 1.98 ms |
| 2 | 984 | 1.02 ms |
| **4** | **4208** | 0.24 ms |
| **8** | **6618** | 0.15 ms |
| 16 | 7086 | 0.14 ms |
| 32 | 7795 | 0.13 ms |

而按 §6.5 的目标负载算：`12.1 条 × 300 req/s = 3630 往返/s` —— **落在容量之内**（4 连接档
就有 4208/s）。**所以"DB 往返"不可能是 ~36 req/s 天花板的来源。§6.3 的判断被推翻。**

⚠️ 注意：单连接 1.98 ms 与 4+ 连接 0.13 ms 差 15 倍，说明**单次往返成本高度依赖并发**
（PG 的组提交 + 协议流水线）。**§6.3 把"单连接测得的 2.96 ms"当成了每次往返的固定成本，
据此乘出"16 条 × 3 ms = 48 ms 地板"，那是把并发下的成本算成了串行成本。**

### 7.3 客户端能推 **997 req/s**（所以"加 worker 在 2 就饱和"不是服务端的锅）

对着一个**零工作量桩服务**（`data/stub_server.py`，秒回 200、无 DB）跑同一个 loadgen：

| 客户端配置 | 实测 |
|---|---|
| 12 workers @300rps | **300 req/s** |
| 60 workers @300rps | **299 req/s** |
| 60 workers @1000rps | **997 req/s** |

⇒ **loadgen 不是瓶颈**。那么 §6.4 的"worker 加到 2 就饱和（37/70/68/62）"就只剩两种解释：
**服务端共享资源**，或**测量装置缺陷**——而 7.4 显示是后者占了大头。

### 7.4 §6 那批数字的**装置缺陷（必须知道，否则会继续误读）**

复测时发现两个**我自己的流程问题**，它们直接污染了 §6 的数字：

1. **残留服务偷偷接客**：一个早先失败的脚本没清干净，它的服务进程一直占着 8812 端口；
   后续每次"新起服务"其实**绑不上端口、卡在启动**，而压测流量**全部打在那个残留服务上**
   ——那个进程用的是**另一套配置**（不同的 pool / worker 数）。于是"新配置"的 A/B 实际
   在测一个配置未知的进程。

   **确切机制（后来查清了，值得单独记住）**：`DD_SERVICE_WORKERS>1` 时 uvicorn 用
   **`multiprocessing.spawn`** 起 worker，这些子进程：
   - 命令行是 `python -c "from multiprocessing.spawn import spawn_main; ..."`，
     **不含 `data_dog.service`** ⇒ 任何"按命令行匹配服务"的清理**全部漏掉它们**
     （本轮实测漏了 **14 个，存活 2.75 小时**）；
   - **继承了父进程的监听套接字** ⇒ 父进程（uvicorn 的 multiprocess manager）退出后，
     **端口仍被它们持有、服务仍正常响应**；
   - `netstat -ano` / `Get-NetTCPConnection` 报的是**已死的父 pid**，`Get-Process` 查不到
     ⇒ 看起来像"残留 TCP 表项"，实际有活进程在服务（`/healthz` 照样 200，还报 uptime）。

   ⇒ **清理必须按"端口 → socket 持有者"或"父进程的子进程树"来做，不能按命令行匹配。**
   这也解释了为什么"真身 pid"时有时无：拿到的往往是中间进程或已死的父进程。
2. **PG 容器的会话残留会让新实例启动挂死**：多次强杀 DB 客户端后，容器里积了 21 个空闲
   连接，此时 PG 形态的服务**永远停在 `Waiting for application startup`**（`py-spy` 显示
   主线程空闲在 asyncio `_poll`，即某个异步 await 不返回；CPU 是启动早期烧的）。
   **`docker restart` 清干净后，同一份代码 1 秒就绪**。⇒ 这个挂死是**环境态**，不是代码。

**因此 §6 的绝对吞吐（34~37 req/s）与 worker 扩展曲线都不可信**，本次全部作废；
本节 7.2 / 7.3 是重测过的（每次都用**独占新端口**并**用监听者 pid 反证**服务身份）。

### 7.5 现在的结论（比 §6 更弱，但更诚实）

- **已确证不是约束的**：DB 往返吞吐（7.2）、loadgen 客户端（7.3）、提交次数（§6.2）。
- **仍然指向服务端 CPU**：PG 形态下真身进程在 60 并发实测吃 **137% 单核**；本轮还观察到
  它在"挂死"状态下 12 秒烧掉 5.1 秒 CPU（≈40% 核）——**这个进程确实很吃 CPU**。
- **但仍未确证**：这 137% 里有多少是"必要的每请求成本"、多少是 60 并发下的线程/事件循环
  开销。**在装置修好、机器空闲之前，我不再给新的绝对吞吐数字。**

### 7.6 下一步（按证据排序，且**先修装置**）

1. **修装置**（不做这步，后面全是白测）：每次用**独占端口** + **用 `Get-NetTCPConnection`
   的 `OwningProcess` 反证服务身份** + 强杀 DB 客户端后**重启 PG 容器**。已落进
   `data/` 下的临时脚本（gitignore）。
2. **在空闲机器上重测 worker 曲线**（1/2/4/8），得到可信的"单进程服务率"与真实扩展性。
3. **只做 T2 批量 upsert**（消掉 4~5 条/请求）：它是明确该做的工程修复，**但按 7.2 的容量
   账，别指望它把中负载 P99 拉进 SLO**。→ **已实施，见 §8。**
4. **诚实的 SLO 结论维持 §6.5**：60 workers @300 rps 下 P99 仍**未达标**；本节的贡献是
   **把"为什么未达标"从三个错误答案（连接池 / 提交吞吐 / 往返次数）里摘出去**，
   并指出**测量装置本身曾是主要噪声源**。

## 8. T2 已实施：业务 upsert 每行 **4 条 → 1 条**（2026-10-10）

§7.6 排的第 3 项。**本轮未跑压测**（按约定压测要先申请窗口），故本节**只给语句数证据，
不给任何吞吐/P99 数字**。

### 8.1 怎么改的

`repository.py` 新增 `_upsert_one_stmt()`：用方言原生的 `INSERT … ON CONFLICT DO UPDATE`
替掉 `_upsert()` 的"`get` → 命中 UPDATE / 未命中 SAVEPOINT + INSERT + RELEASE"。

- **竞态从"被兜住"变成"不存在"**：旧写法的 SAVEPOINT 是为了扛"并发两个请求同时 `get`
  到 None"（实测 8 并发写同一 id 有 2 个抛 `IntegrityError`）。`ON CONFLICT` 把同一件事
  交给数据库**原子**完成，**没有"先查后插"的窗口**。
- 列值构造抽成 `_candidate_values()` / `_telemetry_values()`（**唯一来源**），`_apply_*`
  改为它的薄包装——ORM 路径与 Core 路径不再各存一份字段清单（两份必然漂移）。
- 方言不支持时**回退**到旧路径：**正确性优先于语句数**。
- **`created_at` 不进更新集**：它是**首次写入**时间，也是 ④ 保留策略的判据。若重复投递
  把它刷新成"刚写入"，一条被反复重投的老事件就**永远不会被清理**——保留策略会**静默
  失效**（不报错，只是数据永远不消失）。有专门的测试钉住这条。

### 8.2 证据：每行语句数（测试实测，**不是压测**）

`tests/test_upsert_single_statement.py` 用挂在 `Engine` **类**上的 `before_cursor_execute`
数语句（挂错对象会一条都抓不到 → 静默假绿，所以刻意挂在类上）：

| 操作 | 旧路径 | 新路径 |
|---|---|---|
| 新增一行遥测 | 4 条（`SELECT` + `SAVEPOINT` + `INSERT` + `RELEASE`） | **1 条** |
| 重复投递同一行遥测 | 2 条（`SELECT` + `UPDATE`） | **1 条** |
| 新增 / 更新一个候选 | 4 / 2 条 | **1 条** |

测试同时断言"**不再出现 `SAVEPOINT`，也不再出现 upsert 前的预查 `SELECT`**"——
这比断言语句总数更耐用：换方言、换写法时，只要那两类语句回来了就会红。

按 §7.1 的清单外推：业务侧每请求约 **6 条 → 2 条**，**每请求总语句 12.1 → 约 8 条（−33%）**。
⚠️ **后一句是外推**（真实每请求总数要在 PG 上重测，而 PG 压测按约定需先申请窗口）。

### 8.3 本节的边界

- **没有新的吞吐/P99 数字**；§6 那批数字**仍然作废**（见 §7.4）。**不要在引用本文时把
  §8 当成"提速 33%"**——减的是**语句数**，不是已实测的延迟。
- 按 §7.2 的容量账（往返通道 4208~7795/s，目标负载只需 3630/s），**本轮本就不该期待它把
  中负载 P99 拉进 SLO**。它是"该做的工程修复 + 少发往返"，不是 SLO 解药。
- **未动**状态层那 5 条/请求（限流 1 次 + 候选分组 1 次 + `build()` 回读 1 次）。要降它们
  得换后端（Redis）或改形状，属另一批。

## 9. 第四次修正：CPU 花在 **HTTP + 落库**，不在数据面（2026-10-10，进程内实测）

§7 把根因收窄到"服务进程 CPU"，但**没量过它到底花在哪**。本节补上，并据此做了一处
可测量的优化。**仍未跑压测**（按约定需先申请窗口）。

### 9.1 三个数放在一起看

| 路径 | CPU/请求 | 墙钟/请求 |
|---|---|---|
| **应用数据面**（`process_one`：网关→解析→归一→窗口→检测→候选，state=memory） | **0.039 ms** | 0.057 ms |
| **HTTP + 落库**（TestClient + SQLite，**不开剖析器**） | **7.76 ms** | 7.80 ms |
| HTTP + 落库 + SQLite，**开 cProfile** | 15.2 ms | — |
| PG 形态端到端（§7 之前那批，**已作废**，仅作量级对照） | — | 74 ms |

**结论**：数据面 0.039 ms（与本文档 §2.1 自己写的"0.05 ms/请求"吻合），
**HTTP+落库是它的 200 倍**。⇒ **墙不在领域逻辑里**；`连接池 / 提交吞吐 / 往返次数 /
领域代码` 四个答案到此全部排除。单核上限按 CPU 算约 **129 req/s**。

⚠️ 口径警告：开剖析器会把 CPU 抬高约 **2 倍**（15.2 vs 7.76）。**拿带剖析器的数去和
不带剖析器的数比是错的**——本节所有对比都在"不开剖析器"下取。

### 9.2 剖析发现的一处纯浪费：每行重建 Core 语句

`coercions.expect` **49200** 次、`schema.__init__` **8400** 次、`_make_proxy`/`visit_bindparam`/
`_append_param_parameter` 各 ~8000 次 —— 即**每请求只执行 2 条语句，却构造了 28 次
SQLAlchemy 语句对象**。原因是 upsert 每行都 `insert(model).values(...).on_conflict_do_update(...)`
**重建整个 Core 语句**，而**语句结构只随表变化、与数据无关**。

### 9.3 已实施：`(方言, 表)` 级语句缓存

`repository._upsert_stmt()` 把语句按 `(dialect, tablename)` **缓存复用**，值改由
`session.execute(stmt, params)` 传入（编译缓存也能命中同一条）。更新列**从表结构推导**
（非主键、非 `created_at`），不再从本次 values 推导——这样"哪些列被覆盖"只写一遍，
**不会与 `_*_values()` 漂移**（漂移的表现是"某列只在某条路径上被更新"，极难发现）。

**实测（同一进程内探针，不开剖析器）**：

| | CPU/请求 | 单核上限 |
|---|---|---|
| 优化前 | 7.760 ms | ~129 req/s |
| **优化后** | **6.510 ms** | **~154 req/s** |

**−16%**。测试 `tests/test_upsert_single_statement.py` 钉住两件事：语句对象**确实被复用**
（`a is b`），以及更新集**与表结构完全一致**（漏一列 = 重复投递时那列永不更新）。

> ⚠️ **绝对值口径警告（2026-10-10 追加，比上一条更严重）**：本节这些**绝对值不可复现**。
> 同一份代码、同一台机器、**不同时段**实测：
>
> | 量 | 时段 A | 时段 B |
> |---|---|---|
> | 应用数据面 CPU/请求 | 0.039 ms | **0.312 ms**（8×） |
> | HTTP+落库 CPU/请求 | 6.51 ms | **16.15 ms**（2.5×） |
>
> 且已排除"两项跑在同一进程里互相影响"这一解释（`--only http` 单跑仍是 16.15 ms）。
> 成因未查明（机器负载 24%、内存 90%，也可能与探针自身的 GC/内存布局有关）。
>
> **因此：**
> - **只有"同一时段、同一探针、前后各跑一次"的对比可信**——上表的 **−16% 是这样做出来的**
>   （独立探针在改动前后各跑一次，口径一致），**这个相对结论保留**；
> - **6.51 / 7.76 / 0.039 / 0.312 这些绝对值都不应当被当成常量引用**（包括写进 SLA 或 README）；
> - 要对外给绝对值，**必须先有一个"机器空闲"的测量窗口**，并在同一窗口内跑完所有对比。
>
> 这条与 §7.4 是同一类教训，而且更根本：**探针本身也是被测系统的一部分；
> 没有受控窗口时，任何绝对性能数字都是噪声。**

### 9.4 剩下的两块（都还没解）

- **HTTP+落库仍有 6.51 ms/请求**：剖析显示它是"千刀万剐"式的框架栈开销
  （Starlette 依赖解析 / pydantic / prometheus / SQLAlchemy 绑定处理），
  **没有单一热点可砍**。要再降需要成体系的改造（绕开 ORM、精简中间件、去掉每请求的
  metrics 标签），**不是一次提交能完成的**。
- **PG 相对 SQLite 多出约 66 ms 墙钟/请求**（74 − 7.8）：这是**进程内 CPU 之外**的部分，
  即往返 + 网络 + pg 客户端栈。它高度依赖部署拓扑（Docker Desktop 端口转发 vs 同机直连），
  **必须在目标拓扑下复测**。

### 9.5 一个**假设**（明确标为假设，不是结论）

`300 req/s × 6.5 ms/请求 ≈ 1.95 核` ⇒ 若 CPU 是唯一约束，**3~4 个 worker 在空闲机器上
有可能达到 300 req/s**。这与 §6/§7 里"2 个 worker 就饱和（~70 req/s）"**矛盾**，
而后者已因测量装置缺陷作废（§7.4）。**孰对孰错只能靠修好装置后的压测判定——本节不做预测。**
