## 关键设计约束

### 1. 单元化：每区一套完整栈，**本地读写**

每区域独立的 api + PG + redis。跨区**不做同步调用**——跨区调用会毁掉延迟与可用性。

### 2. 数据边界优先**按租户/车队就近归属**

**最省事的冲突规避**是让同一条数据**不被两区同时写**：把设备/车队归属到就近区域，
其数据只在该区产生。**改设备归属比写消解逻辑容易得多**。
双向复制的冲突消解是**兜底**，不是常态——`dd_replication_conflicts_total{path="concurrent"}`
持续增长即说明数据归属划分有问题。

### 3. 确定性 ID 是收敛的天然基础

候选/事件/幂等键的 ID 由输入 `sha256` 派生（`alerting/outbox.py`），**全局确定**——
两区对同一 Episode 算出**同一个** `event_id` → 复制后是**同一条记录**，天然收敛，
无需消解。这是既有设计的红利。需消解的只有**可变状态**（alert 状态机 / severity / ack）。

### 4. 表清单：只复制**需要跨区共享**的表

并非所有表都要复制。审计/日志类通常**本地留存即可**，跨区复制只增负担。
发布集应**显式列举**需共享的业务表，而非 `FOR ALL TABLES`。

### 5. 冲突消解的位置

复制工具（pglogical 等）通常自带 LWW（last-write-wins）——但 LWW **依赖时钟**，
跨区时钟偏移会导致**非确定**结果。本项目**不用** LWW 收敛业务状态，而是把业务的
**revision** 作为因果序、并在应用层用 `resolve_two` 做**确定性**消解（告警取更严重、
ack 取先到）。复制工具负责**搬运**，应用负责**收敛**。

## 诚实边界

- **RPO > 0**：异步复制本质。要 RPO=0 需数据库**同步复制设施**（PG `synchronous_commit`
  + 多数派），牺牲可用性与延迟，**非应用代码可解**。
- **本机无法验证**：本目录的配置需**真实多区基础设施**才能 apply 与验证。
  本机单区环境**做不了**——如实标注，不假装已测。
- **不做自动脑裂恢复**：主选举依赖外部共识（etcd/Consul），自研必错。
